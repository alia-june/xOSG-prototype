# Universal Program Wrapper Architecture v0.1

## 1. Boundary

```text
caller / JSON / IPC
        |
        v
+--------------------------+
| Universal Program Wrapper|
|--------------------------|
| envelope + version       |
| schema validation        |
| operation registry       |
| introspection            |
| adapter dispatcher       |
| provenance carriage      |
| result normalization     |
+-------------+------------+
              |
       +------+------+
       |             |
       v             v
 native adapter   legacy CLI adapter
                     |
                     v
               exact executable
```

Optional layers surround, but do not become, the wrapper:

```text
sf-Program-Access / containment / policy
                 |
                 v
       Universal Program Wrapper
                 |
       +---------+---------+
       |                   |
  BitCore hook       Program adapter
  (optional)              |
                          v
                       program
```

## 2. Core objects

### WrapperManifest
Defines one wrapped program, wrapper version, program identity, adapters, declared operations, evidence level, schemas, and limits.

### OperationDefinition
Defines stable `operation_id`, optional human alias, input fields, adapter binding, declared side effects, evidence level, and output contract.

`operation_id` is canonical inside UPW. It may be an opaque bitcode supplied by an external BitCore registry. UPW does not infer semantics from the value.

### RequestEnvelope
Carries protocol version, request ID, request kind, operation identity, input payload, provenance, authority context, and execution options.

### ResponseEnvelope
Carries request ID, wrapper outcome, raw program result, normalized result, diagnostics, provenance, and evidence.

### Adapter
Translates one validated request into a program-specific invocation and translates the result back into the canonical response.

## 3. Separation of concerns

```text
AUTHORITY CONTEXT carried by UPW != authority granted by UPW
DECLARED capability             != tested capability
RAW exit code                   != normalized outcome
PROGRAM artifact                != process instance
OPERATION definition            != invocation
ALIAS                            != canonical operation identity
```

## 4. Adapter contract

An adapter receives:

```text
manifest
operation definition
validated request
authority/provenance metadata (read-only carriage)
```

It returns:

```text
raw execution result
normalized result
diagnostics
evidence generated by this invocation
```

Adapters must not silently broaden argument scope, substitute executables, invoke through a shell by default, or convert unknown results into success.

## 5. Legacy CLI path

```text
structured JSON
    -> operation lookup
    -> input validation
    -> argv construction
    -> exact executable selection
    -> constructed environment
    -> subprocess(shell=False)
    -> capture stdout/stderr/exit
    -> parser/normalizer
    -> canonical JSON response
```

## 6. Native adapter path

Embedded callers may register a native handler against an `operation_id`. Native handlers receive structured data directly; they do not simulate argv. The standalone CLI reference does not dynamically import arbitrary native code.

## 7. Introspection

The wrapper exposes the following control operations in v0.1:

- `describe`
- `operations`
- `schema`
- `version`
- `status`
- `invoke`

These describe the wrapper/program boundary. They do not imply that a legacy program natively supports them.

## 8. Failure model

Fail closed at the wrapper validation boundary for malformed envelopes, unknown operations, invalid inputs, missing executable paths, unsupported adapter types, or ambiguous adapter definitions.

Program failure is reported, not rewritten as wrapper protocol failure unless the wrapper itself failed to perform the invocation.
